# Branching Tree Technique (BTT) Test Suite

This directory contains tests following the **Branching Tree Technique (BTT)**, a structured approach to test case design that ensures comprehensive coverage of all possible scenarios and edge cases.

## Strict BTT Rules

This test suite follows **strict BTT** - each leaf in a `.tree` file MUST map to exactly one test function. The following rules are enforced:

### 1. One-to-One Leaf Mapping
- Each leaf in the `.tree` file corresponds to exactly one test function
- No duplicate test functions covering the same leaf
- No overlapping test cases that satisfy multiple branches

### 2. Explicit Branch Scoping
- Every test function MUST include ALL modifiers that scope it to a unique leaf
- For tests with multiple branches (e.g., `execType: DEFAULT vs TRY`), each test MUST explicitly include the branch modifier
- Example: `test_WhenTheTargetCallReverts()` MUST include `givenTheExecutionModeExecTypeIsDEFAULT` if that's its branch

### 3. Explicit Revert Selectors (Specification-Driven)
- **NEVER** use bare `vm.expectRevert()` without a selector
- **ALWAYS** specify the exact error selector: `vm.expectRevert(ErrorName.selector)`
- For errors with parameters, use: `vm.expectRevert(abi.encodeWithSelector(Contract.ErrorName.selector, param1, param2))`
- This ensures tests fail for the right reason and catch regressions

### 4. Tests Define Specification, Not Implementation
- **Tests define what SHOULD happen, not what currently happens**
- If the implementation uses bare `require()` or wrong error, the test should still use the CORRECT expected error
- **Failing tests indicate implementation bugs that need fixing** - do NOT change tests to match buggy implementation
- Example: If spec says "should revert with InvalidRootValidation" but implementation uses `require(x > 0)`, test MUST use `vm.expectRevert(InvalidRootValidation.selector)` and fail until implementation is fixed
- This approach ensures tests serve as living documentation of expected behavior

### 5. Test Base Class
- All BTT test contracts MUST extend `BTTModifiers` (not `Test` directly)
- This ensures access to common setup (kernel, ep, validators, etc.)
- New test files should follow the pattern of existing BTT tests

### 6. No Bulloak Separators in Final Code
- After running `bulloak check --fix`, manually remove any `BULLOAK AUTOGENERATED SEPARATOR` comments
- Deduplicate any functions that bulloak couldn't merge automatically
- The final code should be clean with no auto-generated markers

### 7. Bulloak-First Workflow (Preventing Duplicates)
- **ALWAYS** run `bulloak scaffold <file>.tree` to generate test skeletons
- **NEVER** write manual tests with different names than bulloak generates
- **ALWAYS** run `bulloak check test/btt/*.tree` before committing (add to CI)
- Function names come from bulloak - modifiers provide scope, not the function name suffix
- If bulloak generates `test_WhenExtraCallReverts()` with modifier `whenAlreadyDeployed`, use that exact name

### 8. Leaf Text Must Be Specific
- Every leaf MUST state the exact expected behavior (error selector / event / return value)
- Do not use vague leaves like "it should revert"
- If the error has parameters, include them in the leaf text

### 9. One Leaf per Test (No Multi-Leaf Assertions)
- A single test MUST validate exactly one leaf
- Do not assert multiple independent leaves in one test
- If multiple outcomes are needed, split into separate tests

### 10. Modifiers Only Set State
- Modifiers MUST only set up state or context
- Modifiers MUST NOT contain assertions or `expectRevert`
- All assertions belong in the test body

### 11. No Test-Level Loops Over Leaves
- Do not iterate through multiple cases in one test
- Each case MUST have its own test function

### 12. Each Test Must Assert Something
- Every test MUST include at least one assertion (assertTrue, assertFalse, assertEq, etc.) or explicit `vm.expectRevert` with a custom error selector
- Comment-only stubs are forbidden
- Bare `vm.expectRevert()` without a selector is NOT allowed - always specify the expected error

### 13. Tree Completeness Check (Hard Gate)
- Every `.tree` file MUST pass `bulloak check test/btt/*.tree` before PR
- CI MUST fail if any leaf is missing
- CI SHOULD fail if any BTT test contains only comments without assertions

### 14. README Sync
- Any new `.tree` file MUST be added to the README table in the same PR

## What is BTT?

BTT organizes test cases in a tree-like structure where:
- **Branches** represent different conditions or states
- **Leaves** represent specific test cases or assertions

### Keywords

| Keyword | Purpose | Example |
|---------|---------|---------|
| `given` | Contract state conditions (setup) | `given the validator is installed` |
| `when` | Function parameters, execution modes | `when the caller is not the EntryPoint` |
| `it` | Test assertions/expected behaviors | `it should revert with Unauthorized error` |

## Naming Conventions

### Modifiers
- `whenXxx()` - Modifiers for "when" conditions
- `givenXxx()` - Modifiers for "given" state conditions

### Test Functions
- `test_WhenXxx()` - Test for successful path
- `test_RevertWhen_Xxx()` - Test for expected revert
- `test_WhenXxx_Description()` - Test with additional context

### Branch Disambiguation
When multiple branches share similar names, suffix with the branch context:
- `test_WhenTheTargetCallSucceeds()` → for DEFAULT execType under SINGLE callType
- `test_WhenTheTargetCallSucceeds_GivenTheExecutionModeExecTypeIsTRY()` → for TRY execType
- `test_GivenCallTypeIsCALL_HookAddress0()` → for hook=address(0) branch
- `test_GivenCallTypeIsCALL_HookAddress1()` → for hook=address(1) branch

```bash
forge test --match-path "test/btt/*.t.sol" -vvv
```

## Using Bulloak

[Bulloak](https://github.com/alexfertel/bulloak) is used to ensure tree-to-test synchronization:

```bash
# Install bulloak
cargo install bulloak

# Check if tests match specification (MUST pass before PR)
bulloak check test/btt/*.tree

# Auto-fix missing tests (then manually dedupe)
bulloak check --fix test/btt/*.tree
```

### Post-Bulloak Cleanup

After running `bulloak check --fix`:
1. Remove all `BULLOAK AUTOGENERATED SEPARATOR` comments
2. Deduplicate any functions with similar names
3. Ensure each leaf maps to exactly one test
4. Add explicit modifiers to scope each test to its unique branch

### Preventing Duplicate/Stub Tests

**Common mistakes to avoid:**

1. **Don't write manual tests with different names than bulloak expects**
   ```solidity
   // BAD: Bulloak generated this stub, but you wrote a different function
   function test_WhenTheTargetCallSucceeds() external { /* empty stub */ }
   function test_WhenSingleCallSucceeds_DefaultExec() external { /* actual test */ }

   // GOOD: Fill in the bulloak-generated stub directly
   function test_WhenTheTargetCallSucceeds() external {
       // actual assertions here
   }
   ```

2. **Don't duplicate scope in function names when modifiers already scope it**
   ```solidity
   // BAD: Redundant suffix - modifier already scopes it
   function test_WhenExtraCallReverts_WhenTheAddressIsAlreadyDeployed()
       external
       whenTheAddressIsAlreadyDeployed
   { }

   // GOOD: Let the modifier provide the scope
   function test_WhenExtraCallReverts()
       external
       whenTheAddressIsAlreadyDeployed
   { }
   ```

3. **Don't leave placeholder tests with only comments**
   ```solidity
   // BAD: Placeholder with no assertions
   function test_WhenTheTargetCallSucceeds() external {
       // it should return the call result
   }

   // GOOD: Concrete assertions
   function test_WhenTheTargetCallSucceeds() external {
       // it should return the call result
       kernel.execute(mode, executionData);
       assertEq(callee.bar(), 1, "Callee should be called");
   }
   ```

### Recommended Workflow

1. **Write the .tree file first** - Define the complete branching structure
2. **Run `bulloak scaffold`** - Generate the initial test skeleton
3. **Fill in assertions** - Add concrete test logic to each generated function
4. **Run `bulloak check`** - Verify tree-to-test mapping before committing
5. **Run in CI** - Add `bulloak check test/btt/*.tree` to CI pipeline

```
Kernel_validateUserOp

```

## Example Test Implementation (Strict BTT)

```solidity
import {BTTModifiers} from "./BTTModifiers.sol";
import {Unauthorized} from "src/types/Error.sol";
import {ValidationManager} from "src/core/ValidationManager.sol";

abstract contract Kernel_validateUserOp is BTTModifiers {
    // Modifiers map to tree branches
    modifier whenCallerIsNotEntryPoint() {
        vm.stopPrank();
        vm.startPrank(makeAddr("randomCaller"));
        _;
    }

    modifier givenValidationTypeIsRoot() {
        _;
    }

    // Tests map to leaves - ALWAYS use explicit revert selectors
    function test_WhenTheCallerIsNotTheAccountItself()
        external
        whenCallerIsNotEntryPoint
    {
        PackedUserOperation memory op = _createBasicUserOp();
        bytes32 userOpHash = ep.getUserOpHash(op);

        // CORRECT: Explicit selector
        vm.expectRevert(Unauthorized.selector);
        kernel.validateUserOp(op, userOpHash, 0);
    }

    function test_GivenTheValidatorIsNotInstalled()
        external
        givenValidationTypeIsValidator
    {
        // For errors with parameters, use encodeWithSelector
        vm.expectRevert(
            abi.encodeWithSelector(
                ValidationManager.InvalidVid.selector,
                validatorToIdentifier(newValidator)
            )
        );
        kernel.validateUserOp(op, userOpHash, 0);
    }
}
```

## Anti-Patterns (DO NOT DO)

```solidity
// BAD: Bare expectRevert without selector
vm.expectRevert();
kernel.validateUserOp(op, userOpHash, 0);

// BAD: Test without explicit branch modifiers
function test_WhenTheTargetCallReverts() external {
    // Which branch? DEFAULT or TRY? SINGLE, BATCH, or DELEGATECALL?
}

// BAD: Duplicate tests covering the same leaf
function test_GivenMsgValueIsSent() external { ... }
function test_GivenMsgValueIsSent_WhenAlreadyDeployed() external { ... }  // Same leaf!
```

## Benefits of Strict BTT

1. **Unambiguous Coverage** - Each leaf has exactly one test, no gaps or overlaps
2. **Precise Failure Detection** - Explicit selectors ensure tests fail for the right reason
3. **Clear Documentation** - Tree files serve as readable specifications
4. **Auditor-Friendly** - Easy to verify test completeness by matching trees to tests
5. **Regression Prevention** - Tests catch the exact error, not just "any revert"
